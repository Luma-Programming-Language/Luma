# Luma v0.3.4 – Self-Hosted

Luma is a systems programming language focused on explicit memory management, fast compilation, and compile-time ownership verification without a borrow checker or garbage collector.

Since v0.2.0 we've rewritten the compiler from scratch, in Luma itself. This release is the first one to ship off that rewrite. The compiler that builds your Luma code is now written in the language it compiles, checks its own build on every commit, and can cross-compile itself to Windows and macOS from a single Linux machine.

---

# Self-Hosting

The old compiler was C on top of LLVM. The new one is Luma, transpiling to C, which `cc` (or a cross toolchain) turns into a native binary. `luma` compiles `luma`.

Every commit runs a two-generation bootstrap:

1. An existing `luma` binary compiles the current compiler source — generation 1.
2. Generation 1 compiles that same source again — generation 2.
3. We diff generation 1 against generation 2, byte-for-byte.

If a compiler can't reproduce itself exactly from its own source, something's wrong, and we don't want to find that out from a user. This runs before anything else does, on every push and every PR:

```text
==> Generation 1: building bin/luma with bootstrap/luma-seed
==> Generation 2: rebuilding with the gen1 output
==> Stable fixpoint confirmed (gen1 == gen2, byte-for-byte)
==> Running test suite directly (bypassing lumix's --no-sanitize default)
==> bin/luma is bootstrapped, self-verified, and passes the test suite
```

Tagging a release now produces verified builds for Linux, Windows, and macOS automatically — more on that below.

# What's New

## Scoped `switch using`

Bare case labels instead of repeating an enum's namespace on every arm:

```lx
const Color -> enum { Red, Green, Blue };

switch using Color (c) {
    Red   -> { output("r\n"); }
    Green -> { output("g\n"); }
    Blue  -> { output("b\n"); }
}
```

You can still write a label fully qualified if you want — the shorthand is optional, and exhaustiveness checking works exactly the same either way.

## Struct Embedding

Structs can embed another struct now, which promotes its fields and methods onto the containing struct:

```lx
const Entity -> struct {
pub:
    x: float,
    y: float,

    move -> fn (dx: float, dy: float) void {
        self.x = self.x + dx;
        self.y = self.y + dy;
    },
};

const Player -> struct {
pub:
    ...Entity,
    name: *byte,
    health: int,

    take_damage -> fn (amount: int) void {
        self.health = self.health - amount;
    },
};

let player: Player = Player { x: 0.0, y: 0.0, name: "Connor", health: 100 };
player.move(10.0, 5.0);   // promoted from Entity
player.take_damage(25);   // Player's own
```

A direct member always wins over a promoted one with the same name:

```lx
const Player -> struct {
pub:
    ...Entity,
    // Shadows Entity's move — this one runs, not Entity's.
    move -> fn (dx: float) void { self.x = self.x + (dx * 2.0); },
};
```

And if you need the embedded struct's own version anyway, you can still reach it explicitly:

```lx
move -> fn (dx: float, dy: float) void {
    Entity.move(dx, dy);   // Entity's own move, once, not Player's override
},
```

## Static Struct Methods

Methods that don't get an implicit `self`, called on the type instead of an instance:

```lx
const Point -> struct {
pub:
    x: float,
    y: float,

    static origin -> fn () Point {
        return Point { x: 0.0, y: 0.0 };
    },

    static at -> fn (x: float, y: float) Point {
        return Point { x: x, y: y };
    },
};

let a: Point = Point::origin();
let b: Point = Point::at(3.0, 4.0);
```

# Cross-Platform

`-t`/`--target-os` actually cross-compiles now. It used to just pick which `@os {}` branches got emitted, while the build step still shelled out to whatever `cc` was on the host — so asking for `windows64` on Linux got you a Linux binary with the wrong platform code baked into it. Not great. The build step now routes non-native targets through [`zig cc`](https://ziglang.org), which brings its own minimal libc and headers per platform, so you get a real Windows or macOS binary from one Linux machine without setting up mingw or osxcross.

We didn't just take that on faith. `luma` cross-compiling itself now produces a real PE32+ Windows executable and a real Mach-O macOS executable, and CI runs both of them — downloads each artifact onto an actual `windows-latest` / `macos-latest` runner and executes it. Zig's not involved at that point, it's a build-time tool same as `cc`. The binary just runs.

```text
smoke-test-windows: success
smoke-test-macos:   success
```

# Hardening

Pushing cross-compilation all the way through surfaced four real bugs, none of which actually had anything to do with cross-compiling. They were just sitting in the code paths nothing had exercised hard before:

- Bare `!` wasn't in the lexer's operator table at all. `!expr` just silently lexed as `expr`, no error, anywhere in the language.
- Prefix `++i`/`--i` returned the wrong value. The increment itself was fine, but the expression handed back the *old* value instead of the new one. You'd never notice in `loop [...](...) : (++i) {}` since nothing reads the value there, but it broke anywhere that did.
- A path-resolution bug could silently shadow a local edit with a stale system-installed copy of the same standard library file. No error, no hint which file actually got used, just quietly wrong behavior.
- `syscall()`'s declaration in `<unistd.h>` depends on the host's default feature-test-macro setup, so the exact same source compiled on one machine and failed on another.

All four are fixed now, with regression tests. Kind of embarrassing to have shipped with any of them, but we'd rather find these ourselves than have someone else do it for us.

# Static Analyzer

Fixed three classes of false-positive leak reports:

- Passing an owned value into a `#takes_ownership` parameter now counts as consuming it, instead of getting flagged.
- `obj.field = value` is tracked as an ownership transfer instead of a leak.
- Reassigning a global or module-level variable no longer gets scoped to whatever function happens to be reassigning it.

While chasing those down we also found two real use-after-free/double-free bugs in the compiler's own code. Not analyzer false positives, actual bugs, now fixed.

- New `-debug` flag.

# Installation

Building from source no longer needs LLVM or Meson, just `cc`:

```bash
git clone https://github.com/Luma-Programming-Language/Luma.git
cd Luma
git checkout v0.3.4

./scripts/bootstrap-build.sh
sudo ./scripts/install.sh
```

Pre-built binaries:

* Linux x86_64
* Windows x86_64
* macOS x86_64

# Breaking Changes

⚠️ The compiler's internals were rewritten from scratch. Existing programs should behave the same as they did under v0.2.0, but this is a new implementation, not a port of the old one; if something regressed for you, please open an issue.

⚠️ Meson, Ninja, and LLVM are gone from the build. Building from source is now just `./scripts/bootstrap-build.sh`.

# Known Limitations

### Cross-Platform

* Windows and macOS builds are cross-compiled from Linux and verified by actually running on real runners, but the compiler hasn't bootstrapped natively on either OS yet (compiling itself, on that OS, with that OS's own toolchain). That's still on the list.
* zig's macOS target is libc-level only, no Cocoa/AppKit or other framework linking. Doesn't affect the compiler itself, but matters if you're linking Luma code against native macOS frameworks.

### Static Analyzer

* Struct methods declared in a `priv:` block aren't typechecked yet.
* Conditional allocation paths can still produce false positives.

### Language

* A multi-variable C-style `for` loop initializer (`for (long long i = 0, long long j = 0; ...)`) emits invalid C.
* No generics yet.
